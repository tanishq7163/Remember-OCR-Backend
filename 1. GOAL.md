You are my senior computer-vision and backend engineer.

We are building **REMEMBER**, a personal memory application whose core purpose is:

> "Save anything. Find it later."

I want you to build the **OCR / Content Extraction Pipeline** for REMEMBER.

IMPORTANT:

OCR and AI understanding must remain separate systems.

OCR's responsibility:

> IMAGE / PDF → RAW TEXT

The LLM's responsibility later:

> RAW TEXT → MEANING / STRUCTURED MEMORY

Do not combine these responsibilities.

---

# 1. GOAL

The OCR system must process:

- Screenshots
- Photos
- Receipts
- Bills
- Posters
- Documents
- Scanned PDFs
- Images containing mixed text
- Indian-language text where the selected OCR provider supports it

and produce clean extracted text plus useful metadata.

Example:

Input:

A screenshot containing:

"MacBook Air M4
₹94,990
Apple India
Available now"

Output:

```json
{
  "text": "MacBook Air M4\n₹94,990\nApple India\nAvailable now",
  "language": "en",
  "confidence": 0.96
}
```

---

# 2. OCR PROVIDER ABSTRACTION

Do NOT hard-code the application to one OCR vendor.

Create an abstraction such as:

```ts
interface OCRProvider {
  extractText(input: OCRInput): Promise<OCRResult>;
}
```

The application should be able to switch between OCR providers later.

Possible providers include:

- Google Cloud Vision
- Azure AI Vision
- AWS Textract
- another reliable OCR provider
- local/open-source OCR where appropriate

Choose one practical provider for the initial implementation, but keep the interface provider-independent.

---

# 3. INPUT TYPES

Support:

### IMAGE

JPEG
PNG
WEBP

### PDF

For PDFs:

Determine whether the PDF contains:

- selectable text
- scanned pages

If selectable text exists, prefer direct text extraction rather than OCR.

If the PDF is scanned, OCR the pages.

Do not OCR everything unnecessarily.

---

# 4. PIPELINE

Build:

FILE UPLOAD
↓
VALIDATE FILE
↓
DETERMINE TYPE
↓
PREPROCESS IF NECESSARY
↓
TEXT EXTRACTION
↓
NORMALIZATION
↓
STORE OCR RESULT
↓
SEND NORMALIZED TEXT TO LLM LATER

The OCR system must never modify or destroy the original file.

---

# 5. IMAGE VALIDATION

Implement:

- MIME validation
- file-size limits
- image dimension limits
- corrupt-image detection
- unsupported-format handling

Do not trust the client-provided MIME type alone.

Validate the actual file where practical.

Reject dangerous/unsupported files.

---

# 6. IMAGE PREPROCESSING

Create an optional preprocessing layer.

Possible preprocessing:

- resize very large images
- orientation correction
- contrast improvement
- noise reduction
- rotation detection
- crop unnecessary borders where appropriate

Do not aggressively alter images.

The original uploaded image must remain untouched.

Preprocessing should only create a temporary OCR copy.

---

# 7. OCR RESULT SCHEMA

Create a structured OCR result.

Example:

```ts
type OCRResult = {
  text: string;
  language?: string;
  confidence?: number;
  pages?: OCRPage[];
  provider: string;
  providerVersion?: string;
  processedAt: Date;
};
```

For pages:

```ts
type OCRPage = {
  pageNumber: number;
  text: string;
  confidence?: number;
};
```

Keep the raw OCR result separate from the final AI-generated interpretation.

---

# 8. TEXT NORMALIZATION

OCR output can be messy.

Implement normalization for:

- excessive whitespace
- duplicated line breaks
- obvious OCR formatting issues
- Unicode normalization
- preserving meaningful line breaks
- preserving prices
- preserving dates
- preserving URLs
- preserving phone numbers

Do NOT aggressively "correct" words using an LLM during OCR.

OCR should produce the closest representation of the source.

AI interpretation happens later.

---

# 9. INDIAN LANGUAGE SUPPORT

Design the system for multilingual content.

Potential languages:

- English
- Hindi
- Hinglish
- Bengali
- Marathi
- Tamil
- Telugu
- Kannada
- Gujarati
- Punjabi
- Malayalam

The exact supported languages depend on the selected OCR provider.

Do not falsely claim support for languages the provider doesn't support.

Store detected language metadata when available.

Mixed-language input must be allowed.

Example:

"₹500 ka recharge karna hai tomorrow"

should remain understandable as mixed-language text.

---

# 10. RECEIPT / BILL HANDLING

OCR should preserve:

- item names
- quantities
- prices
- subtotal
- tax
- total
- date
- store name
- invoice number

Do NOT make OCR itself responsible for calculating totals.

It only extracts source information.

The LLM/structured extraction layer can interpret it later.

---

# 11. DOCUMENT HANDLING

For PDFs:

If selectable text exists:

```text
PDF
↓
Text extraction
↓
Normalized text
```

If scanned:

```text
PDF
↓
Render pages
↓
OCR each page
↓
Combine results
```

Maintain page numbers.

This is important because later the application should be able to tell the user:

> "This information was found on page 4."

---

# 12. STORAGE

Store:

- original file reference
- extracted text
- OCR status
- OCR provider
- OCR version
- detected language
- confidence
- processing timestamp
- page-level results where applicable

Do NOT store unnecessary duplicate copies of the original file.

---

# 13. PROCESSING STATES

Implement:

```text
PENDING
PROCESSING
COMPLETED
PARTIAL
FAILED
```

Example:

User uploads an image.

Immediately:

> Saving...

Then:

> Remembered ✓

If OCR is still processing:

> Understanding image...

If OCR fails:

> We saved your image, but couldn't read the text.

The user must never lose the original memory because OCR failed.

---

# 14. ASYNCHRONOUS PROCESSING

Do not make file upload wait for OCR if OCR may take significant time.

Prefer:

UPLOAD
↓
SAVE MEMORY
↓
RETURN SUCCESS
↓
PROCESS OCR
↓
STORE OCR RESULT
↓
TRIGGER LLM PROCESSING

For the MVP, keep this simple.

A background-job abstraction is fine, but do not introduce Kafka/Kubernetes or an unnecessarily complicated distributed system.

The architecture should work with a simple job mechanism initially.

---

# 15. ERROR HANDLING

Handle:

- OCR timeout
- provider unavailable
- invalid file
- corrupt image
- oversized image
- unsupported language
- empty OCR result
- scanned PDF failure
- provider rate limits

Retry transient errors with bounded retries.

Do not endlessly retry.

If OCR permanently fails:

Keep the original memory.

Mark:

OCR_FAILED

and allow the user to retry later.

---

# 16. SECURITY

This application contains private user content.

Implement:

- authenticated requests
- user ownership checks
- private storage
- signed URLs where appropriate
- file-size limits
- MIME validation
- rate limits
- no sensitive content in production logs

Never expose another user's uploaded files.

---

# 17. COST CONTROL

Avoid unnecessary OCR calls.

Do not process the same file repeatedly.

Use:

- content hash
- processing status
- OCR version

to determine whether OCR needs to run again.

If the same exact file is uploaded by the same user, consider reusing the previous OCR result where appropriate.

Do not make cross-user content sharing assumptions.

---

# 18. OCR + LLM HANDOFF

The OCR service must produce a clean interface for the LLM service.

Example:

```ts
{
  memoryId: "memory_123",
  sourceType: "IMAGE",
  extractedText: "...",
  language: "en",
  pages: [...]
}
```

The LLM then receives this normalized representation.

The OCR system should NOT:

- classify memories
- create embeddings
- answer questions
- generate summaries
- invent missing text
- decide what the user meant

Its job ends at:

# IMAGE → TEXT

# 23. DEFINITION OF DONE

This should work:

USER:

Uploads screenshot:

"MacBook Air M4
₹94,990
Apple"

SYSTEM:

Saves original image.

OCR:

"MacBook Air M4
₹94,990
Apple"

Stores OCR result.

Then passes normalized text to the separate LLM Memory Understanding Engine.

The LLM can then determine:

```text
Product: MacBook Air M4
Price: ₹94,990
Brand: Apple
Category: Product
```

The two systems must remain independently testable.

The fundamental architecture is:

# OCR = WHAT DOES THE IMAGE SAY?

# LLM = WHAT DOES IT MEAN?

# EMBEDDING = HOW IS IT RELATED TO OTHER MEMORIES?

# SEARCH = CAN WE FIND IT LATER?

Now inspect the existing REMEMBER repository and implement the OCR pipeline without breaking existing functionality.
